# 场景搭建 Runtime 目标设计

第一个业务模块为场景搭建，URDF 导出本轮不设计。总体架构见[后端与数据](backend.md)。

## 所有权和调用

借鉴 Kinex 的业务 Runtime、Pi Extension 桥和具体实现分离：`packages/core` 管理实际需要复用的通用能力；`packages/scene` 提供场景能力及其 Python 实现。Node 场景 Runtime 是进程内对象，按 Dai 项目 ID 获取，不按会话或 cwd 合并。Pi Extension 将工具名、参数、项目与会话身份、取消和必要的询问传给 Runtime；前端手动操作也必须经相同场景命令和提交服务。

Runtime 管理自身工作、资源和计算进程。Python 负责场景几何计算；视口截图和用户交互属于前端/宿主，通过受控桥接提供。场景能力直接由 Python 实现，第三方 MCP 通过 Pi package 接入。

不为所有项目在应用启动时创建 Runtime 或 Python worker。场景显示可从持久资源恢复；真正计算时才按需创建 Runtime 和 worker。同一项目的会话复用该项目 Runtime 和 worker；当前 worker 空闲默认五分钟后停止，后续计算时再启动，不影响已保存场景。切会话不擅自停止共享 Runtime，不同项目的数据和任务相互隔离。

## 进程和资源

Node/Python 协议需版本、请求身份、操作、参数、取消、进度和成功/失败状态；stdout 与日志分离，不能假定中断的计算已提交。大型几何资源通过受控文件交付，规定临时目录、路径检查、大小、所有权和清理。worker 崩溃、超时或重启时不重放副作用；已提交场景仍是权威来源。长计算的取消必须在实际阻塞计算的情况下验证，必要时停止并重建自身拥有的进程，不能关闭其他项目使用的资源。

当前 worker 的单条 JSON 响应上限为 8 MiB，按 UTF-8 字节计算；STEP 源文件与生成的 GLB 各限 256 MiB，单次导入限 10 万对象、200 万三角形和 256 层。响应包含对象元数据，复杂模型可能在达到对象数上限之前先触及 8 MiB。超过限制会报错，不提交场景。真实 STEP 回归使用一个方盒的 5000 个重复实例，验证了 5001 个对象导入、超过 1 MiB 的响应契约校验、持久化和重启恢复，源文件哈希不变；该测试不能保证任意复杂的 5000 对象模型都满足响应上限，也未验证该规模下的 Electron 界面性能。更大规模需要后续评估分页或受控文件传输。

外部 STEP 原路径需有授权、类型及内容版本校验；读取期间改变或重新定位到不同内容不能当作原版本。对象和重复实例、源文件版本、坐标系和单位需要稳定定义，重新导入不可假设对象身份自动不变。前端展示与 Agent 所读结构均来自一致的场景版本；版本过期应拒绝写入并返回当前状态。

用户可通过文件选择器重新定位源 STEP。后端对所选文件计算 SHA-256，仅与原内容一致且场景版本未变化时更新路径；模型身份、对象位姿及关节保持不变，源文件不复制。校验期间检查文件身份和修改信息，源文件后续再变化时精确计算仍会拒绝。当前不提供不同内容的自动映射。

同一项目的 STEP 导入和会话运行互斥：导入期间发送会被拒绝，会话运行期间开始导入也会被拒绝。取消导入或会话完成后可继续；不同项目互不阻塞。这样会话不会在导入尚未完成时将旧场景当作导入结果。

### 暂存写入和平台限制

Python 直接从 OCCT 的三角网格编码 GLB，OCCT 不再按可替换的暂存路径创建 GLB 或 `.bin.tmp`。POSIX 平台逐级使用目录句柄和 `O_NOFOLLOW`，以 `O_EXCL` 创建暂存文件，通过已打开的文件句柄写入，并通过目录句柄验证、重命名和清理。自动回归在写入前及重命名前分别把暂存项替换为指向外部文件的符号链接和硬链接，验证外部文件未被覆盖且导入失败。目录被替换时也会拒绝提交。这解决了原 OCC 路径重定向造成的外部文件覆盖，不代表抵御可修改进程内存或持有更高权限的攻击者。

资源接管通过固定目录句柄和文件句柄校验并复制产物，再以排他方式发布，避免校验后的目录或文件替换造成外部文件删除或错误内容提交。当前接管实现依赖 Linux 的 `/proc/self/fd`；macOS 和 Windows 会明确拒绝场景导入，直到实现并验证对应的安全句柄方案。上述保护不构成对不可信同用户进程的完整沙箱。

为避免在身份检查后删除被替换的目录项，接管暂不删除成功导入的 staging GLB 和资源临时项。重复导入相同资源时，临时项也可能是独立副本，磁盘占用会持续累积；失败、取消或恶意替换也可能留下临时项。恶意占用最终哈希名称时，重试可能报告资源损坏。安全的残留清理和恢复机制仍待实现。

Linux worker 重启时仅清理有完整租约、原创建进程已退出且文件身份匹配的受控普通临时文件；活进程文件、未知旧 tmp、链接、未完成登记和已提交资源保留。非 Linux 暂不自动清理。

## 范围和验证

按阶段提供 STEP 导入、结构/显示、对齐/旋转、对象删除与简化、关节候选和用户确认。能否从几何推断出的事实必须有依据；限位、类型或其他必要信息不可靠时请求用户补充。不同源文件可加入同一个项目场景；添加、替换、取消和失败保留语义见 [前端与交互](frontend.md)。

当前实现支持装配导入、局部位姿、对象子树删除、世界保守包围盒和对齐原点；删除只改变场景，不修改原始 STEP 或 GLB。解析圆柱面只作为带单位的局部几何候选，轴向正负不代表运动方向，不自动推断连接关系、关节类型或运动限制。用户可明确指定父子对象、关节类型和必要轴线，保存草稿并在专用入口确认；相关对象变化后候选会标记过期或失效，限位仍为未知。网格简化、完整几何修复、运动仿真和 URDF 导出尚未实现。包围盒是保守近似，复杂单位、工业样本和平台兼容性仍需验证。

`scene_measure_distance` 可只读重解析当前项目中两个几何叶对象各自已授权的 STEP，校验源哈希和场景 revision，应用当前 Z-up 世界刚体位姿后返回 OCCT BRep 算法的 `shapeDistanceM`。返回值受 CAD 算法和几何容差影响，不是数学上无误差的距离；完全包含、交叉和接触都可能得到零。`surfaceDistanceM` 固定为 null，`collision` 固定为 unknown；`innerSolution` 为真时两个点也为 null，不将内部点误称为表面接触点。真实测试覆盖重复实例、不同 STEP、父级旋转、编辑后位姿、相离/接触/交叉/完全包含、源变更/缺失及运行中取消。复杂曲面、退化几何、大型工业模型和跨平台表现尚未充分验证。

GLB 编码使用紧凑的浮点与索引数组，分配每个面的数组前按大小限制检查；256 MiB 限制是资源大小限制，并非进程总内存上限。OCCT 网格生成和 GLB 缓冲仍需额外内存，复杂模型可能消耗大量内存。测试覆盖合成 STEP 的层级、实例、颜色、单位、盒体法线和圆柱侧面法线，以及内存 XCAF 的正负尺度；不代表已验证工业 STEP 的复杂样式、镜像与性能。业务 Python 包依赖的第三方几何库仍包含原生代码。

### 显示网格精度 PoC

在临时目录生成了一个真实 STEP 装配：圆柱半径 0.1 m、高 0.2 m，包含两个重复实例和红色材质。分别从 STEP 重新生成两档显示网格：

| 采样设置（线偏差 / 角度） | 独立几何三角形数 | GLB 大小 | 圆柱侧面边中点最大径向采样偏差 |
| --- | ---: | ---: | ---: |
| 5 mm / 0.8 rad | 60 | 4,056 B | 约 1.921 mm |
| 0.1 mm / 0.1 rad | 500 | 17,372 B | 约 0.0311 mm |

该样本两档的节点层级、实例位置、颜色和重复实例共享几何均一致，源 STEP 字节及解析圆柱半径未变。这是**显示网格的重新采样，不是 BRep 简化**；上述误差仅是此圆柱侧面边中点的采样结果，不是通用几何的 Hausdorff 上界。PoC 脚本位于临时路径 `/tmp/dai-mesh-quality-poc.py`，没有接入生产。

生产实现仍需验证复杂工业 STEP 的层级、面映射、网格缺失、误差与性能，明确质量参数和错误报告；生成独立产物后须通过场景 revision 检查及原子提交，不能以此 PoC 认定通用模型的简化能力已完成。

### 场景资源的读取与显示

后端只向桌面进程返回已授权资源的项目身份、大小与媒体类型；桌面不再接受并重新打开后端返回的文件路径。Linux 启动时固定数据根目录句柄，并通过 `/proc/self/fd` 与 `O_NOFOLLOW` 逐级打开项目、场景和资源目录以及资源文件。读取器按声明大小（最多 256 MiB）读入独立缓冲，在发送前验证 SHA-256；`GET` 和 `HEAD` 都需要通过校验。资源校验后不再重读源 inode，因此路径替换、父目录替换及同 inode 内容改变不会把未经校验的数据交给前端；取消与退出会关闭相关句柄，退出期间活跃读取保留根句柄直到结束。

此实现为 Linux 专用：当前缺少 macOS 和 Windows 上经实机验证的目录句柄方案，因而这些系统的场景资源读取明确失败，不能宣称已跨平台支持。每次请求最多需缓冲 256 MiB，协议响应可能额外复制数据；当前最多同时执行两个读取，复杂大型场景的内存和性能需进一步验证。上述措施确保返回内容与授权哈希一致，不代表阻止了同用户其他进程修改应用数据或对应用进行拒绝服务。

桌面启动时固定数据根目录句柄，并将该句柄的设备号和 inode 作为身份传给后端；场景目录创建、产物接管及 Python worker 均对实际打开的根目录重新核对身份。运行中切换数据根符号链接或替换其实际目录时，场景导入会拒绝，不向新根写入。设置、凭据、会话与包使用启动时解析的规范路径，避免之后更换配置链接导致重定向；但 SQLite、普通设置和会话文件并未全部改为目录句柄访问，若规范根本身被同用户进程替换，不能宣称全应用数据已得到相同隔离。

Linux 桌面初始化也使用目录句柄：从已有的规范祖先逐级打开或创建数据根，并在固定的根句柄下创建应用子目录，再将该句柄交给资源读取器。显式指定的数据根符号链接在启动时解析并固定其当时的目标；启动期间祖先或根目录被替换时，路径与句柄身份检查会拒绝继续。该机制不证明在首次启动、固定身份之前用户指定的链接未被同用户其他进程预先改动；这种场景需要可信的外部身份记录或禁止符号链接。非 Linux 启动路径尚未实机验证。
